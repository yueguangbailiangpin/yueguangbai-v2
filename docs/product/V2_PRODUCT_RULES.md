# V2 产品与业务规则

## 1. 沟通和正式事实

私人微信负责日常沟通、提醒和关系维护。

以下内容必须通过门户或内部受控页面成为正式事实：

- 产品申请和需求批次；
- 预约；
- 订单号、订单日期、最终支付金额和截图；
- 评论资料和审核结果；
- 买家返款；
- 卖家本金、服务费和结算；
- 财务更正、冲正；
- 客户身份变更和账号启停。

门户第一版提供问题反馈和资料补充，不开发完整实时或多轮客服聊天。

## 2. 客户模型

- 一个卖家客户对应一个全局卖家组织。
- 一个卖家组织可以有多个成员。
- 一个卖家通常有 5–20 个店铺。
- 店铺归属固定并且只属于一个 Marketplace，不因员工或成员调整而改变。
- 一个卖家组织可以在多个 Marketplace 拥有店铺。
- 平台稳定代码首批为 `AMAZON_JP`、`AMAZON_US`、`COUPANG_KR`；韩国站默认禁用且 Adapter 不可用。
- 一个平台产品标识在同一 Marketplace 只能属于一个权威店铺；Amazon 使用 ASIN Adapter 校验。
- 卖家组织内所有 ACTIVE 员工均可为本组织创建授权店铺；内部总管理员或卖家对接员工在 `SELLER_MANAGE`、Personal DENY、Marketplace 与卖家组织范围校验后也可创建。

### 客户会话与退出

- 买家页面保留“退出登录”，成功后按共享 Customer Cookie 归属清理 Buyer 与 Seller 两个 Customer Query Root。
- 卖家页面不提供“退出登录”入口，不新增 Seller 退出按钮、页面动作、替代路由或专门测试。
- 卖家没有主动退出入口不等于取消安全失效：账号类型不匹配、已验证的 Customer 401、Session 失效、凭证重置及其他既有失败关闭场景，仍必须执行共享 Customer logout/失效清理并清空两个 Customer Root；不得泄漏或继续显示旧身份数据。
- Customer 清理不得影响独立 Staff Session；403/404 也不得被误当成退出或 Session 失效。

## 3. 产品与需求

产品是长期主数据，需求批次是一次数量计划，两者不能混用。

### 产品申请

卖家成员提交：

- 店铺；
- ASIN/产品编号；
- 产品中文名；
- 搜索词；
- 产品链接；
- 图片；
- 备注。

审核结果：审核中、通过、拒绝、撤回。

### 需求批次

产品申请与投放共用卖家“商品与投放”入口。产品申请仍先进入独立审核；产品通过后，卖家可在同一流程继续提交投放批次。批次至少包含：

- 产品；
- 目标数量；
- 任务/评论类型；
- 买家可见说明；
- 内部说明；
- 状态。

追加需求必须新建批次，不覆盖旧批次。

### 预约下单排期

- 新产品版本必须同时保存“每隔 N 个自然日、每次 M 单”，N/M 均为正整数；后续调整必须新增产品版本，不能覆盖旧版本。
- 卖家不填写开放、预约或下单截止时间；服务端按版本化排期策略生成并保存合法窗口，并把策略版本写入提交审计。Staff 审核发布时只确认首个下单日期，并预览完整窗口与理论最后下单日期。
- 卖家请求不得提交时间窗口 override；如未来保留特殊 override，只能由具备排期权限的 Staff 提供原因、预览哈希、幂等键和版本确认。
- 有效队列只有 `PENDING_REVIEW` 与 `APPROVED`，按 `submitted_at ASC`、不可变预约 ID `ASC` 排名；拒绝、取消和过期退出当前排名但保留历史。
- 排名 r 的批次为 `floor((r-1)/M)`，预计日期为首单日期加“批次 × N”个北京时间自然日；周六、周日和所有节假日都计入，不接入节假日日历。
- `target_quantity` 的最后理论名额不得晚于需求下单截止日；冲突时发布或改期失败关闭。
- 已发布需求只能由总管理员或卖家对接在服务端预览影响人数、前后日期后，以 `expected_version`、预览哈希、幂等键和原因确认；排期版本只追加、不覆盖。
- 0037 前的产品版本和需求没有完整排期事实时统一显示“尚未配置排期”，不得根据当前默认值伪造历史日期。
- 预计日期只用于内部协作，不创建或覆盖订单资料、平台下单日期、正式订单和财务快照。

## 4. 预约

买家只能看到已发布的公开需求。

预约流程：

```text
买家提交预约
→ 系统预检
→ 暂时记录候选
→ 售前人工批准或拒绝
→ 批准后锁定名额
→ 买家在期限内提交订单资料
```

预检至少检查：

- 买家启用状态；
- 买家身份是否待人工核对；
- 相同需求/ASIN历史参与；
- 有效名额；
- 当前截止时间；
- 既有未完成预约；
- Marketplace。

同一买家在同一店铺同时只能保有一条 `PENDING_REVIEW` 或 `APPROVED` 预约；该限制按店铺而非产品/ASIN 判断。买家产品投影必须稳定返回“不可预约：该店铺已有进行中预约”的资格和原因，但提交命令及其最终原子写入仍须重复校验，防止跨产品并发预约绕过限制。被拒绝、取消或过期的终态预约立即释放该店铺资格。

领取、批准、取消、过期和重开必须有状态事件。

### 下单指引

- 预约批准只创建 `UNPUBLISHED` 指引，不向买家提前显示下单任务。
- Staff 发布时直接使用已审核产品版本的有序搜索关键词文字，不再生成或发送关键词图片。
- 指引进入 `ACTIVE` 后，买家任务/指引页显示店铺名称、搜索关键词、商品主图、规格、金额、截止时间和可见备注；买家据此直接搜索下单。
- 指引版本持续引用不可变产品版本，有序关键词进入内容哈希；不可因取消图片生成而取消权限、幂等、版本、状态机、Audit 或 Outbox。
- 既有关键词图片和生成记录仅作历史兼容与审计保留，新指引版本不再产生关键词图片。
- 买家读取指引状态或内容是只读操作，不能因页面访问把指引过期、重开 Staff 工作项或改变待办；到期由既有受控的 expiry/reconciliation 路径处理。`ACTIVE` 指引、发布事实和 Staff 工作项完成必须在同一事务内一致。

## 5. 待核对订单资料与正式订单

买家提交的订单信息先进入“待核对资料”，不是正式订单。

必须提交：

- 平台订单标识（Amazon 站点为 Amazon 订单号）；
- 平台订单日期；
- 最终实际支付金额及显式 ISO 币种；
- 订单截图；
- 可选备注。

售前确认后才：

- 认领订单号；
- 生成或确认订单组；
- 首次正式订单时生成买家编号；
- 锁定买家日汇率；
- 锁定卖家协议汇率版本；
- 锁定服务费规则版本；
- 保存产品、店铺、卖家、买家和需求快照；
- 生成正式订单和审计事件；
- 更新需求批次进度。

同一订单号正常只认领一次。少数历史同订单号跨店铺情况必须进入人工冲突处理，不自动复制。

## 6. 金额和汇率

### 最终支付金额

订单权威金额为订单截图显示的最终实际支付金额。金额使用整数最小单位和显式 ISO 币种；JPY/KRW 为零位小数，USD/CNY 为两位小数。

### 买家日汇率

- 方向：站点交易币种 → CNY，整数值和明确比例尺；
- 每个中国业务日期、来源币种和 CNY 组合一条；
- 不允许使用缺失日期的前一天或最近值自动回退；
- 正式订单确认时保存快照；
- 历史快照不受后续修改影响。

### 卖家协议汇率

- 属于卖家组织，不属于产品；
- 同一卖家组织同一业务币种共用一条协议汇率；
- 版本化；
- 卖家对接提交变更，管理员确认；
- 仅影响生效后的新正式订单。

### 卖家本金汇率策略（Migration 0041）

- 卖家应返本金的最终汇率 = 平台下单日的权威日基准汇率 + 卖家本金汇率加点。Amazon 使用正式订单 `amazon_order_date`，该日期按中国业务自然日口径与日汇率匹配；不得使用确认日或最近日期替代。
- 加点是绝对汇率增量，不是百分比或 basis points。当前 JPY→CNY 使用固定整数刻度；例如基准 `0.051`、加点 `+0.004` 得最终 `0.055`。
- 配置按币种对提供默认值，并可按卖家组织覆盖；组织覆盖优先。没有覆盖的组织与明确设置为 `0` 的覆盖必须在数据上可区分。
- 策略版本必须带生效时间、提交/确认审计身份、决策版本和幂等边界；只影响生效后的新正式订单。卖家端不能修改策略。
- D1 必须拒绝直接插入非 `SUBMITTED` 初始状态、非法状态转换、终态/事件改删、重复 pending 或重复 confirmed 生效边界；快照必须证明基准日等于平台下单日，默认策略组织为 NULL，组织覆盖等于正式订单卖家组织。
- Staff 工作台提供默认/覆盖读取、明确 `+0` 展示；GLOBAL Owner 可提交默认或组织覆盖，Seller Ops 只提交其已分配组织覆盖，Owner 负责确认/拒绝；策略 API 成功与失败均为 `no-store`，不通过卖家端或 Personal DENY 绕过。
- 正式订单确认必须将平台下单日、基准汇率版本和值、实际采用的策略范围/版本/加点、最终汇率、`HALF_UP` 取整口径和本金计算结果写入不可变快照；D1 guard 必须拒绝不一致的本金金额。`SELLER_PRINCIPAL_RATE_ENFORCEMENT_ENABLED` 默认关闭，先部署 schema/工作台，再创建并确认默认策略和验证日汇率，最后由单独授权开启；开启后缺少下单日权威汇率或生效策略时确认失败关闭，历史订单和既有账务不得重算。
- 该策略只调整卖家本金；买家返款、服务费、退款、评论和其他财务口径继续沿用既有规则。

### 服务费

- 规则键：卖家组织 + Marketplace + 任务/评论类型；
- 类型至少：rating、text、image、video；
- 版本化；
- 正式订单时锁定规则版本；
- 评论审核通过时生成应收服务费事实。

## 7. 评论与原业务模式

按业务所有者决定保留原模式：

```text
评论资料提交
→ 售后审核
→ 审核通过
→ 买家返款变为应付
→ 卖家服务费变为应收
```

系统只管理内部流程，不自动操作 Amazon 账号、评论发布、修改或删除。

评论状态只能通过评论工作流修改。审核通过必须在同一业务命令中：

- 校验状态和版本；
- 保存审核事件；
- 锁定评论类型；
- 生成买家返款应付；
- 生成卖家服务费应收；
- 创建 D1 权威工作项与内部 Outbox；
- 返回可重放结果。

审核通过后的更正必须使用更正单，明确选择保留或冲正已产生的财务事实。

## 8. 买家返款和卖家结算

### 买家返款

应返金额基于订单快照。实际转账由售后录入：

- 应付金额；
- 实际金额；
- 差额（系统计算：实际 - 应付）；
- 转账时间；
- 凭证；
- 备注。

已完成记录不可直接编辑或删除。

### 卖家本金和服务费

本金与服务费是两个独立结算组件：

- 本金应付/已结算/无需结算；
- 服务费未产生/应付/已结算/无需结算。

卖家门户只能看到其组织和授权店铺的卖家侧金额。

### 内部结算与利润

至少提供：

- 预计利润；
- 财务已完成利润；
- 内部已结算利润；
- 现金差额；
- 最终实现利润。

所有报表都由不可变财务事实聚合，不允许用户直接填写利润。

## 9. 图片

- R2 是正式在线图片源。
- 图片通过授权 API 读取，不公开裸 R2 Key。
- 客户可见性按图片种类、客户组织和字段白名单决定。
- 所有图片或文件证据入口统一支持点击选择、拖拽和剪贴板粘贴，并提供预览与单个删除；交互方式不得绕过原有格式、大小、数量、权限和上传验证规则。
- 买家返款凭证、私人微信截图和内部备注默认不可见给卖家。
- 第一版不从 Google Drive 实时回源。
